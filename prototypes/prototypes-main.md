# 사이비 호텔 — 프로토타입 실험 전체 계획

**v0.3 · 2026-10-29 · 실험 전**  
기준: rules.md v0.4, 보조: terms.md·ability_checklist.md. 구성: 공통 문서 1개 + 실험 문서 10개.

## 1. 실험 동기

확인하려는 재미는 **배치한 엔진의 성취, 직원으로 개입하는 판단, 융합으로 새로운 법칙을 만드는 발견, 파괴 뒤 다시 설계하는 즐거움**이다. 이 구조가 실제로는 정답 반복, 대응 불능, 제작법 암기, 복구 노동으로 경험되는지 짧은 장면에서 확인한다.

각 프로토타입은 독립된 상황·메커니즘·시작 상태를 사용할 수 있다. 완성된 경영 루프를 먼저 만들 필요는 없다. 아래 내용은 실험 계획이며 실제 참가자 평가나 확정된 재미 개선 결과가 아니다.

이번 개정에서는 공통 설명을 이 문서에 모으고 구현 검산·코딩 validation 항목을 삭제했다. 구현 정확성과 코드 테스트는 코딩 에이전트가 담당한다. 개별 문서는 **플레이할 장면, 비교 방법, 유저스터디 질문, 경험 판단, 검증 UI**에 집중한다.

## 3. 규칙과 실험 후보의 경계

- 원본의 **드로우 → 주사위 확인 → 직원 사용 → 이동·효과** 순서, 주사위 눈과 마나의 관계를 따른다(rules.md §4.3~4.5).
- 통과와 도착을 구분하며 도착 타일에서도 통과 효과가 먼저 발생한다. 일반 손님은 출구 첫 도달·통과 때 퇴장한다(§5.1~5.4).
- 직원 풀·편성 덱·손패는 서로 다르다. 융합은 직원 풀의 해당 직원을 소모하며, 대체 직원이 있으면 편성 덱 장수는 유지할 수 있다(§3.1·§4.1~4.2).
- 확장과 안정 운영은 의도된 성장·성취다. 늘 같은 스타일을 선호하거나 안정적으로 수익을 낸다는 사실만으로 실패로 보지 않는다(§7.2·§8.6).
- **융합 방식·인원·무작위성·공개 정보는 미정이다.** P4의 방법과 공개 범위는 채택 후보이며, 다른 실험이 편의상 쓰는 융합 방식도 정식 확정이 아니다(§3.4~3.5).
- 각 문서의 수치·자산·공급·손실 조건은 그 실험에만 적용한다. P4·P9는 직원 A~H를 사용하는 확장 콘텐츠를 두되, 결과 종류와 효과는 각 문서를 따른다. 다른 프로토타입에 자동으로 추가하지 않는다.
- 제외한 모듈은 시작 때 알린다. 직원 시스템을 제외한 장면은 정식 0장 덱의 플레이가 아니다. 각 실험에서 정한 공개 범위 밖의 미래 주사위와 진행자 해법은 제공하지 않는다. **융합 결과의 공개는 P4의 조건별 지시**를 따른다.

## 4. 실행 순서와 운영

| 단계 | 실험 | 다음에 확인할 것 |
| --- | --- | --- |
| 핵심 행동 | P1·P2·P4·P9 | 배치·개입·융합·재설계 각각의 매력과 이해 부담 |
| 제약 | P3·P6·P8 | 제약이 추가하는 판단과 없애는 선택권 |
| 성장·시간 | P7·P10·P11 | 투자 회수, 성취 이후 상실, 반복 운영 |
| 짧은 결합 | P1+P2, P4+P9, P3+P6 | 단독 실험에서 보이지 않은 정보·판단 부담 |

P9는 융합 방법 확정 전에도 임시 조회 방식으로 시작할 수 있다. P10은 P9에서 대체 구성을 만드는 경험이 성립한 뒤 진행한다. P11은 익숙한 호텔의 반복과 처음 보는 표시의 이해를 구분한다.

첫 파일럿은 실험당 4~6명 정도로 시작하되, 비교 조건마다 여러 사람의 경험이 확보되도록 회차를 나눈다. 이는 문제 발견용 규모이며 통계적 입증을 뜻하지 않는다. 한 사람에게 모든 문서를 연속 수행시키지 않는다. 경험한 장르, 조건 순서, 힌트 여부, 중단 이유를 기록한다.

기본 흐름은 **시작 상태 안내 → 독립 선택·실행 → 자유 설명 → 질문별 점수 → 필요할 때 도움 후 재시도 → 조건 비교**다. 같은 사람이 여러 조건을 경험하면 순서를 번갈아 배정한다. 이미 배운 방법·정답의 영향이 큰 경우에는 첫 노출 참가자를 나눈다. 도움 후 결과와 최초 경험은 따로 본다.

## 5. 유저스터디: 질문–5점 응답

개별 문서의 각 질문에 **1~5점 중 하나를 선택해 `질문 — 응답 x/5` 쌍으로 기록**한다. 문서의 `__/5`는 빈 응답란이다. 여기에 적힌 기준은 실제 측정 결과가 아니다.

| 점수 | 의미 |
| --- | --- |
| 1/5 | 전혀 그렇지 않다 |
| 2/5 | 대체로 그렇지 않다 |
| 3/5 | 반반이다 |
| 4/5 | 대체로 그렇다 |
| 5/5 | 매우 그렇다 |
| N/A | 해당 경험을 하지 못했거나 판단할 수 없다. 0점이나 중간 점수로 바꾸지 않음 |

각 문항에는 **이유 한 줄과 기억나는 장면**을 함께 받는다. 이해도·선택권·즐거움·성취·다음 시도 의향을 따로 평가하고 합산 점수 하나로 줄이지 않는다. 조건 직후 독립적으로 답하게 한 뒤, 모든 평가가 끝나면 선호 조건과 포기한 장점을 묻는다. 질문의 의미는 설명하되 특정 점수로 유도하지 않는다.

### 경험 판단 기준

- **진행 신호:** 개별 문서가 지정한 핵심 문항 각각의 중앙값이 4/5 이상이고, 구체적인 긍정 이유와 실제 선택·설명이 부합한다. 초기 의사결정을 위한 임시 기준이며 출시 합격선은 아니다.
- **보완 신호:** 이해는 높지만 선택권이나 즐거움이 낮음, 재미는 있지만 부담이 큼 등 차원별 불일치가 나타난다. 문항별 1~2점 응답을 따로 읽고 원인 후보를 한 번에 하나씩 바꾼다.
- **유보:** 경험하지 않은 항목이 많거나 조건별 첫 노출·도움 여부가 섞여 비교하기 어렵다. 미응답·중단을 숨기지 않고 필요한 장면을 추가한다.

높은 공포 수익·빠른 해결·많은 클릭은 재미를 대신하지 않는다. 반대로 중단이나 낮은 성공률만으로 재미가 없다고 단정하지 않는다. 서로 다른 선호가 유지되면 단일 승자를 강제로 고르지 말고 대상이나 선택권을 검토한다.

## 6. 검증 UI 공통 구성

| 화면 | 필요한 구성 | 목적 |
| --- | --- | --- |
| 시작 안내 | 실험 장면, 이번 목표, 사용 자산, 제외된 시스템. 가설의 정답을 암시하지 않는 조건 이름 | 무엇을 경험하는지 알게 함 |
| 플레이 | 실험별 지도·손패·자산과 선택 도구. 현재 조건에서 허용한 정보 표시 | 해당 메커니즘을 직접 경험 |
| 결과 복기 | 자신의 선택과 실제 결과, 지난 장면 보기, 자유 설명 | 점수의 이유가 되는 장면 확보 |
| 질문 평가 | 질문별 1~5 선택 버튼, 척도 설명, 이유·장면 입력, N/A, 다음/제출. 기본 선택 없음 | `질문–x/5` 평가를 일관되게 수집 |
| 비교·다음 선택 | 모든 조건 평가 후 자신의 응답을 나란히 제시. 선호 이유와 추가 시도/종료 선택 | 장단점과 실제 지속 의향 확인 |
| 진행자 검토 | 참가자×조건×문항 점수표, 문항별 응답 수·중앙값·1~2점 수·N/A 수, 발언·행동·도움 여부 | 경험 패턴별 판단과 후속 실험 선택 |

개별 문서는 이 틀에서 무엇을 표시·조작하고 어떤 질문과 연결할지 지시한다. P10처럼 단계별 감정이 중요한 경우에는 지정 시점에 질문한다. 코딩 검사 화면이나 자동 합격 판정은 이 문서 범위에 포함하지 않는다.

## 7. 기록과 결과 정리

| 참가자 / 조건 / 첫 노출 여부 | 질문 ID | 점수 /5 또는 N/A | 이유·장면 | 실제 선택·설명 | 도움·중단 |
| --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |

결과는 **문항별 분포 → 이유와 행동 → 원인 후보 → 다음 변경** 순서로 정리한다. 조건 비교에는 실제 응답 인원을 표시한다. 같은 사람이 답한 비교인지, 별도 참가자 집단인지 구분하고 작은 점수 차이를 일반적인 우열로 확대하지 않는다.

융합 방법 결정 후에는 직원 소모의 기회비용, 취소·환급, 재모집, 장기 발견 피로를 후속 과제로 다룬다. P9에서 확인한 조합 다양성은 채택한 융합 방법과 결합해 다시 경험을 확인한다.
